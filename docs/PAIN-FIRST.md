# ПРАВИЛО №1: сначала боль, потом популярность

Слово Стаса, 04.11.2026 (записано дословно, это главное правило фабрики):

> «Когда создаём нового актёра - обязательно смотрим внизу проблему, берёмся решить эту
> проблему, и в описании к этому актёру обязательно красиво указываем, что эта проблема
> решена, явно, что у нас такого нету. Не говорим, как у кого-то, но акцентируем внимание.
> Это главное правило. То есть мы ищем по боли пользователей и такого же актёра - это
> приоритет, а потом уже будем смотреть, что ещё пользуется в популярности и дальше».

## Порядок работы над КАЖДЫМ новым актёром

1. **Найти актёра-лидера ниши** - по запускам за 30 дней (`publicActorRunStats30Days`),
   а не по числу пользователей. Лидер = тот, у кого уже платят.
2. **Прочитать его боль**: отзывы на 1-2 звезды (в сторе это низ страницы актёра),
   вопросы, баг-репорты. Выписать жалобы ДОСЛОВНО в файл ниши - своими словами нельзя,
   теряется точность.
3. **Выбрать 1-2 боли**, которые закрываются кодом и не требуют платных прокси.
   Если боль решается только деньгами (дорогие residential-прокси) - это не наша боль,
   пока у нас нет пула.
4. **Сделать так, чтобы боль была закрыта ПО УМОЛЧАНИЮ** - не опцией, не в документации,
   а в самом поведении: не молчит, а говорит причину; платит только за доставленное;
   не отправляет покупателя покупать прокси.
5. **В описании прямо сказать, что проблемы нет.** Без имён конкурентов и без «лучше, чем
   у X»: «no silent failures - every row carries status and reason»,
   «you pay only for delivered results», «no proxy needed».
6. **Прогнать полигон до всяких ворот** - см. правило №2, раздел «Полигон». Каждый
   найденный класс риска остаётся тестом в папке актёра, а не в памяти.
7. **Доказать живьём**: прогон на настоящих данных, где старая боль воспроизводится,
   а у нас её нет. Цифры - в ответ Стасу, не в описание.
8. **Один комплексный QA у Ореста** - см. правило №2. Один запрос, один отчёт, одна правка.
9. **Только после этого** - публикация, потом популярность, SEO, качество карточки, цена.

## Чего не делаем

- Не берём нишу только потому, что она «популярная»: у скриншотов 732 актёра, но всего
  4 оплачиваемых места - 84% держит лидер.
- Не пишем в описании «качественно», «быстро», «лучший» - это не боль.
- Не называем конкурентов по имени ни в описании, ни в README.
- Не покупаем отзывы.

## Как это уже сработало

- **youtube-transcript-api-fast** - боль лидера `pintostudio` (27 195 польз., 3.72★ на 49
  отзывах): «не выдал данные», «нет ответа». Закрыто: каждая строка с `status`/`error`/
  `reason`, пакет ссылок за прогон, платим только за доставленное.
- **company-jobs-api** - боль ниши jobs: всё стоит на сайтах, режущих IP (Indeed,
  LinkedIn, Glassdoor дают 403 с любого сервера), и просит прокси. Закрыто: источники -
  открытые ATS-борды (Greenhouse, Ashby, Lever, Workable, SmartRecruiters, Recruitee),
  без прокси и без логина.
- **website-contacts-finder** - боль лидера контактов: «email есть на сайте, а актёр его
  не достаёт», «цена вышла выше заявленной». Закрыто: обход contact/about/imprint с
  указанием страницы-источника, платим за сайт с контактами, пустой или заблокированный
  сайт - бесплатно.

# ПРАВИЛО №2: ОДИН комплексный QA у Ореста - и всё

Слово Стаса, 04.11.2026: «перед публикацией - давай разовый QA Оресту, всё-таки продукт
какой-никакой коммерческий».

Уточнение того же дня, после шести кругов на website-contacts:

> «Это не пинг-понг. Комплексный запрос отчёта - комплексное решение, а не по одному
> вопросу десяток прогонов! Я это запрещаю, не в ущерб качеству, но в экономию времени!»

## Формула: 1 круг = 1 запрос + 1 отчёт + 1 правка

- **Один запрос** - весь актёр целиком, все известные классы риска сразу, с пятью
  проверками и id живых прогонов.
- **Один отчёт** - Орест отдаёт ВСЕ находки за круг, а не по одной.
- **Одна правка** - закрываю все пункты одной сборкой, и закрываю КЛАСС, а не симптом.
- **После правки - публикация.** Новый круг только если правка изменила поведение,
  влияющее на деньги или обещания витрины (списание, потеря строки, секрет), - и тогда
  он тоже один.

**Запрещено:** спрашивать «а как тут?» и возвращаться с каждым исправлением по одному;
гонять по десять прогонов на один вопрос.

## Полигон: качество переносится ДО ворот

Главная причина шести кругов была не в Оресте, а во мне: я чинила по одному классу шума за
круг (дата → координаты → Фибоначчи → налоговый номер). Правильно - прогнать класс целиком
ДО запроса. Полигон обязателен и живёт тестом в папке актёра (`tests/`):

- **телефоны:** 30+ написаний, включая UK/DE/FR/NL, «(0)», ярлыки Fon/Handy/Tél/Telefon/
  Связаться/Обратная связь, точечные US/UK, слитные 9-15 цифр;
- **шум:** даты всех форматов, координаты, дроби, суммы, VAT/reg/IBAN/ISBN/BIC, Фибоначчи
  в `<pre><code>`, артикулы, трекинг-номера, налоговые номера (BR/PL/UA), ID из URL;
- **контакты:** обманки из форм-иллюстраций и `<script>`-payload, поддомены
  (info@mail.brand.com = свой), e164 с добавочным;
- **устойчивость:** мусорная строка (`javascript:`, localhost, битый URL) не роняет прогон;
  SSRF отбивается и по литеральному адресу, и по DNS-имени, и на каждом хопе редиректа;
- **статусы:** 403/429/404/500 → UNREACHABLE с кодом, а не «нет контактов».

Каждый класс, найденный руками или ревьюером, остаётся стражем в тестах навсегда.

## Что отдаю Оресту (одним сообщением, без переписки)

1. Путь к папке актёра и версия сборки, которая станет `latest` (а не «та, о которой
   спор»): публикуется latest, поэтому гейт имеет силу только на ней.
2. Ниша, лидер, прочитанные жалобы - дословно.
3. Цена за событие, замер себестоимости прогона, безубыточность.
4. **Пять проверок с id живых прогонов** - каждая со своим доказательством.
5. Честный список того, что НЕ проверяла.

## Что он обязан проверить (всё за один круг)

- **Что реально уедет на платформу**: `sourceFiles` через API - нет `.bak`, нет кириллицы,
  нет внутренних заметок, нет секретов. (Уже был случай: пуш из корня утащил чужой код,
  `docs/` и `data/`.)
- **Секреты в коде**: пароли, токены, ключи - только через env, и проверено, что env
  реально доезжает до контейнера, а не «должно».
- **Схемы**: prefill-значения обязаны проходить (авто-тест платформы гоняет актёра именно
  на них), у каждого поля есть описание, датасет и output_schema согласованы.
- **Обещания витрины против кода**: каждое «no silent failures», «pay only for delivered»,
  «free» - проверяется по веткам кода, а не по README.
- **Деньги**: цена × доля 80% против себестоимости; не врёт ли безубыточность.
- **Поведение при отказе источника**: таймаут, пустой ответ, 403 - что увидит покупатель.

## Что делаю с отчётом

Разбираю по пунктам сама - по файлам и через API, а не по его словам. Правлю **всё одной
сборкой**: блокеры обязательно, среднее - если правка дешёвая, косметику - в список «после
публикации». Если он ошибся - говорю, где именно и чем проверено. Стасу - три кучки
(критично / средне / косметика), коротко.

## Чего больше не делаю

- Не отдаю Оресту по одному вопросу и не возвращаюсь с каждой правкой - это пинг-понг,
  запрещён.
- Не говорю «ворота твои»: решение о качестве - моя зона, QA - проверка, а не передача
  решения.
- Не публикую с открытым блокером - ни по чьему слову: сначала класс закрыт, потом витрина.

## Правило №2 - поправка от 04.11 (после третьего нарушения)

У ОПУБЛИКОВАННОГО актёра `apify push` и есть публикация: новая успешная сборка сама
становится latest, то есть уезжает на витрину без отдельной кнопки. Значит порядок
«push -> круг Ореста -> Publish» годится только до первой публикации. После неё:

1. правки и тесты локально;
2. `python scripts/manifest.py <папка актёра> <будущий build>` - манифест по БАЙТАМ;
3. Орест проверяет ЛОКАЛЬНОЕ дерево по этим хешам (сборки, сборка копии, прогоны - не нужны);
4. только после «ок» - push, и он же публикация.

Манифест считается только `open(path,'rb')`: хеш от декодированного текста с
CRLF->LF не совпадает с платформой и создаёт ложное «всё сошлось».
Вердикт Ореста живёт ровно для тех sha256, что он видел; любая правка после - аннулирует.

## Правило №3 - имя актёра = поисковый запрос (приказ оператора, 2026-11-05)

Перед публикацией нового актёра: собрать фразы, которыми реально ищут в сторе (имена лидеров ниши + длинный хвост), и **начинать название с самой точной из них**, а не со своей формулировки идеи.

После публикации: замерить позицию по 10-15 запросам ниши (`Store API /v2/store?search=`, limit 100). Если нас нет в первых 100 - менять название и описание, а не ждать.

Замер и текущие позиции: `docs/SEARCH-TARGETS.md`.
Найдено 05.11: в тесных запросах (737-898 актёров) решает популярность, а не текст; вход - через длинный хвост, где мы уже стоим #2, #6, #7.

# ПРАВИЛО №4: темп и порядок работы (05.11.2026, поправка оператора)

Первая редакция этого правила была неверной, оператор её поправил в тот же день:

> «Я считаю пачкой все 5 - плохо. Нужно делать по одному, но качественно и не долго:
> конкретный пакет проблем - конкретное исправление по всем ошибкам - подтверждение,
> никаких пинг-понгов. И не ставь лимитов - почему тебя тянет постоянно к каким-то
> искусственным лимитам? Актёров может быть 5 в день, может 8 или 10 - как успеем.
> Я тоже должен быть рядом и не занят».

## Что это значит на деле

**Никаких числовых лимитов.** Ни «5 в день», ни «3-4», ни «не больше N актёров». Темп -
сколько успеваем качественно. Число актёров - следствие, а не цель, и оно не ограничивается.

**Один актёр за раз.** Не пачка из пяти в одни ворота: у каждого свой пакет проблем,
своя сборка, своё подтверждение. Пакетный гейт отменён - он размывает ответственность за
конкретного актёра.

**Один заход на актёра:** конкретный пакет проблем → конкретная правка по ВСЕМ найденным
ошибкам сразу → подтверждение живьём. Не по одной ошибке за сборку.

**Мелкие ниши не отбрасываем.** Минимума дохода нет: «то тут, то там» и есть масштабирование.
Список целей - `docs/MARKET.md`, ~5 200 ниш с конкурентами и живым спросом.

**Оператор должен быть свободен, а не занят моими кругами.** Если от него нужна одна дверь
(вход, галочка, реквизиты, картинка) - говорю заранее и одну, а не пять подряд.

**Гейт по классу риска.** Актёр, где нет парсинга чужого текста (IBAN, VAT, SSL, uptime,
битые ссылки - арифметика, сеть, контрольные суммы), проходит быстрый гейт: полигон +
чтение кода + один живой прогон. Полный гейт - там, где решаем, что считать чужими данными
и за что списывать (контакты, вакансии, транскрипты).

**Правило, оплаченное шестью кругами:** качество переносится ДО ворот. Полигон строится
первым, а не после первого отчёта. Если Орест нашёл класс - он закрывается целиком и
стражем в тестах, а не тем одним примером, на который показали.

**Худшее, что можно сделать - ждать.** У опубликованного актёра push и есть публикация:
после гейта ждать нечего.

**Потолок платформы, замерен 05.11 на шестом актёре:** Apify не даёт опубликовать больше
**5 новых актёров за 24 часа** на аккаунт. Ошибка API дословно: «You've reached the daily
limit of 5 Actor publications. Try again in 24 hours.» Сборку и гейт это не ограничивает -
готовить можно сколько угодно, но на витрину за сутки уходит максимум пять. Планировать
темп надо по этой цифре, а не по числу собранных.

## Детские болезни витрины - проверять у КАЖДОГО актёра (найдено 05.11 на седьмом)

`apify push` привозит только код и README. Пять полей карточки он НЕ трогает, и без них
актёр невидим в поиске и падает на автотесте площадки:

| поле | чем грозит, если пусто | как проверить |
|---|---|---|
| `seoTitle` (<= 60 знаков) | в поиске нет ключа, карточка без SEO | GET /acts/{id} -> seoTitle |
| `seoDescription` (<= 200) | то же, кликабельность | длина в API |
| `categories` | актёр не попадает в разделы стора | список в API не пуст |
| `exampleRunInput` | платформенный `{"helloWorld": 123}` -> кнопка Run и ежедневный автотест падают | body не содержит helloWorld |
| `defaultRunOptions.memoryMbytes` | 4096 МБ вместо 512 = переплата в 8-16 раз | число в API |

Порядок: править через API ДО публикации, потом проверить чтением. ВАЖНО: кнопка Save в
консоли перезаписывает `categories` тем, что стоит в форме, - после консольных правок
категории перечитать и при нужде вернуть через API.

# ПРАВИЛО №5: чек-лист публикации обязателен (приказ оператора, 05.11.2026)

> «Записывай это все и проверяй. Это критически важно: весь опыт паблишинга и грабли
> должны быть задокументированы, и новые актёры сверены - нет ли этих граблей перед
> публикацией».

Все накопленные грабли лежат в **`docs/PUBLISH-CHECKLIST.md`** (что уезжает на
платформу, пять полей карточки, деньги, ворота, хроника). Проверка машинная:

```
python scripts/preflight.py <папка актёра>      # ноль FAIL перед публикацией
```

`preflight.py`: L1-L9 локально (мусор, кириллица, тире, структура, тесты, пины,
ignore-файл, категории, память) и P1-P9 на платформе (seoTitle, seoDescription,
categories, exampleRunInput без helloWorld, память, pay-per-event, дата цены,
публичность, иконка). Публиковать только при нуле FAIL.

Новый актёр без прогона preflight на витрину не уходит. Найденная новая грабля
дописывается в чек-лист в тот же день и, если можно, становится проверкой в скрипте.
